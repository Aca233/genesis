# 管理面板任务处置工作台设计

日期：2026-07-29
状态：已获用户确认

## 1. 背景

现有管理面板按“用户、世界、任务、模型、审计”等数据类型分区，功能完整，但不适合管理员最常见的工作：排查失败任务。故障信息被拆散在总览、任务列表、模型调用、世界和审计页面中，管理员难以快速回答以下问题：

1. 现在有哪些任务需要处理？
2. 哪些故障影响了用户，严重程度如何？
3. 任务在哪一步失败，为什么失败？
4. 应该重新执行、取消，还是继续观察？
5. 操作后任务发生了什么，是否已经恢复？

现有操作还依赖浏览器原生 `window.prompt` 收集原因和确认文字；刷新入口固定跳转 `/admin`；失租告警无法直接下钻；审计查询故障会被空数组掩盖。这些问题共同造成“找不到功能、看不懂数据、操作繁琐、信息不连贯”。

## 2. 目标

把 `/admin` 从数据总览改造为面向值守任务的“任务处置工作台”，让管理员在一个连续上下文中完成：

> 发现故障 → 判断影响 → 理解原因 → 执行处置 → 验证结果

成功标准：

- 管理员进入 `/admin` 后，无需切换页面即可看到所有当前需要人工判断的任务。
- 每条故障都能解释“发生了什么、影响谁、失败在哪一步、建议怎么处理”。
- 管理员可在保留上下文、筛选和列表位置的情况下重新执行或取消任务。
- 操作前后都有明确反馈，不使用原生 `prompt`，不只显示笼统的“成功/失败”。
- 总览告警可直接下钻到对应任务集合或具体任务。
- 查询失败与真实空数据必须在界面上可区分。

## 3. 非目标

本次不做：

- 全局命令面板或复杂快捷键系统。
- 实时轮询、SSE 或 WebSocket。
- 查看用户正文、模型 Prompt、模型 Response 或密钥。
- 在网页中重启应用、数据库、队列或服务器。
- 重写现有权限、安全审计和任务状态机。
- 引入新的 UI、状态管理或测试依赖。

## 4. 信息架构

### 4.1 导航分组

桌面侧栏按管理员任务重新分组：

- **处置**
  - 任务工作台：`/admin`
  - 全部任务：`/admin/tasks`
- **对象**
  - 用户：`/admin/users`
  - 世界：`/admin/worlds`
- **观测**
  - 模型调用：`/admin/llm`
  - 管理审计：`/admin/audit`

“任务工作台”显示需要处理的任务数量；“模型调用”可以显示近期失败数量。移动端保持同样的逻辑顺序，使用可横向滚动的紧凑导航，不隐藏关键入口。

### 4.2 `/admin` 工作台

页面从上到下分为四层：

1. **值守摘要**
   - 失败任务数
   - 租约过期任务数
   - 连续失败任务数
   - 今日已恢复任务数
2. **快速筛选**
   - 需要处理
   - 失败
   - 失租
   - 连续失败
   - 任务、用户或世界关键词
3. **故障队列**
   - 严重程度
   - 任务类型与 ID
   - 用户与世界
   - 失败阶段
   - 故障分类
   - 持续时间
4. **任务详情面板**
   - 发生了什么
   - 影响对象
   - 当前/失败阶段
   - 开始时间与持续时间
   - 尝试次数
   - 数据写入风险
   - 建议操作
   - 任务时间线
   - 关联模型调用、世界和审计入口
   - 允许执行的管理操作

桌面使用列表与详情并列布局；窄屏使用“列表 → 详情”的纵向布局。详情必须可深链，刷新或返回时能够恢复当前筛选和选中任务。

### 4.3 `/admin/tasks` 全部任务

保留完整任务列表用于历史和非故障任务检索，并新增以下筛选：

- `attention=yes`：所有需要人工判断的任务。
- `stale=yes`：活动状态且租约已过期的任务。
- `repeated=yes`：创世任务或叙事任务处于 `failed` 且 `attempt >= 3`。现实改写目前没有持久化尝试次数，首版不标记为连续失败。
- 现有任务类型、状态和关键词筛选继续保留。

从工作台进入全部任务时，URL 必须携带筛选参数，避免管理员再次筛选。

## 5. 故障队列语义

新增统一的只读故障条目 DTO，屏蔽创世任务、生成请求和现实改写任务之间的表结构差异：

```ts
type AdminAttentionTask = {
  kind: AdminTaskKind;
  id: string;
  label: string;
  status: string;
  stage: string | null;
  severity: "high" | "medium";
  reason: "failed" | "stale" | "repeated_failure";
  owner: { id: string; name: string; email: string } | null;
  world: { id: string; name: string } | null;
  startedAt: Date | null;
  updatedAt: Date;
  leaseExpiresAt: Date | null;
  attempt: number | null;
  errorSummary: string | null;
  impactSummary: string;
  recommendation: "rerun" | "cancel" | "observe" | "inspect";
};
```

故障严重程度必须由纯函数根据明确规则计算并单元测试，不能由组件临时推断。首版规则：

- 高：`repeated_failure`；或活动任务的租约已过期至少 10 分钟。
- 中：单次 `failed`；或租约过期不足 10 分钟。

“需要处理”只包含当前仍需人工判断的条目：创世任务和叙事任务的 `failed`，以及三类任务中处于各自活动状态且 `leaseExpiresAt < now` 的任务。已成功、已取消或已经恢复的历史记录不进入队列。

重新执行、取消、恢复和观察建议由任务类型与现有服务端 mutation 允许的状态矩阵派生；如果系统无法证明某操作安全，详情只提供“进一步检查”，不能展示可执行按钮。

## 6. 任务详情与信息连贯性

详情面板以管理员能够理解的顺序组织信息，不直接堆叠数据库字段：

1. **发生了什么**：使用任务类型、状态、阶段和脱敏错误生成一句可读摘要。
2. **影响谁**：显示用户、世界及是否阻塞用户继续操作。
3. **执行到哪里**：展示阶段、尝试次数、租约和关键时间点。
4. **数据是否安全**：明确是否已经写入内容、重新执行是否可能重复。
5. **下一步建议**：根据任务状态显示重新执行、取消、观察或进一步检查。
6. **相关证据**：关联模型调用、审计记录、世界和用户元数据。

详情中的关联入口必须携带任务、用户或世界筛选参数，打开后直接显示相关记录。不得展示用户正文、模型原始输入输出或未脱敏错误。

## 7. 管理操作

### 7.1 命名

现有“安全重试”在界面上统一命名为 **“重新执行”**，辅助说明为：

> 保留失败记录，从允许恢复的位置重新开始。

内部 action 名称和服务端状态机无需为了文案修改。

### 7.2 操作面板

`AdminActionButton` 不再调用 `window.prompt`。改为受控操作面板，展示：

- 操作名称
- 目标任务、用户或世界
- 当前状态
- 操作影响
- 原因输入框及长度要求
- 永久操作所需的确认文字
- 字段级校验错误
- 提交中、成功和失败状态

重新执行流程：

1. 管理员在任务详情点击“重新执行”。
2. 操作面板说明旧失败记录会保留，并显示是否存在重复写入风险。
3. 管理员填写至少两个字符的处置原因。
4. 客户端提交现有 `/api/admin/actions` 端点。
5. 服务端继续负责权限、状态、租约、幂等和审计校验。
6. 成功后关闭操作面板，刷新当前路由数据，保留 pathname、筛选和选中任务。
7. 详情显示新状态、审计记录入口和“继续观察/返回队列”入口。

失败时保留输入内容，在面板内显示服务端返回的中文错误；不得退化为 `alert` 或笼统的“管理操作失败”。

### 7.3 刷新

顶栏“刷新数据”改为客户端刷新按钮，调用 `router.refresh()`。它必须保留当前路径、页码、筛选参数和选中任务，不再导航到 `/admin?refresh=1`。

## 8. 数据流与边界

- 页面继续采用 Next.js 16 Server Components 加载管理数据。
- 筛选、分页和选中任务使用 URL search params，保证可分享和可恢复。
- 仅操作面板、刷新按钮及必要的局部交互使用 Client Components。
- 管理操作继续通过 `/api/admin/actions`，不新增重复 mutation 入口。
- 工作台数据查询返回显式状态：`data | unavailable`。查询失败不得用空数组冒充“没有记录”。
- 所有管理查询继续使用显式 Prisma `select`，遵守现有正文与密钥隔离边界。
- 页面不增加轮询；操作完成后只通过 `router.refresh()` 获取最新状态。

实现前必须阅读仓库内 `node_modules/next/dist/docs/` 中与 Server Components、`searchParams`、导航和 `router.refresh()` 相关的 Next.js 16.2.10 文档，不依据旧版 Next.js 习惯实现。

## 9. 错误与空状态

界面必须区分：

- **真实空状态**：当前没有需要处理的任务。
- **筛选无结果**：没有符合当前条件的任务，并提供清除筛选入口。
- **部分数据不可用**：例如审计查询失败，但任务队列仍可显示。
- **页面级失败**：核心任务查询不可用，显示重试当前视图入口。
- **操作校验失败**：字段级提示，不清空输入。
- **操作状态冲突**：说明任务状态已经变化，并刷新当前详情。

总览中的审计、模型或统计查询失败时必须显示“数据暂不可用”，不得显示“暂无记录”。

## 10. 视觉与响应式原则

- 优先可读性和处置效率，不继续增加同尺寸指标卡。
- 正文和关键数据字号不得低于现有管理台的可读下限；辅助文本不使用难以辨认的微型字号。
- 严重程度不能只依赖颜色，必须同时提供文字或图标标签。
- 交互目标满足键盘操作、可见焦点和合理触控尺寸。
- 桌面并列展示队列与详情；移动端不隐藏关键字段，而是改为分组档案布局。
- 操作确认使用语义明确、可聚焦的受控面板；不得使用 `window.prompt`、`window.alert` 或连续浏览器弹窗。

## 11. 测试与验收

### 11.1 单元与数据测试

- 故障严重程度计算。
- 失租任务识别与查询条件。
- 连续失败识别规则。
- “需要处理”不包含终态任务。
- 任务详情摘要和建议操作派生。
- 审计/统计查询故障返回 `unavailable`，不返回假空数组。
- 重新执行继续遵守现有状态、租约、幂等和审计约束。

### 11.2 组件与交互验证

在不新增依赖的前提下，为可提取的纯逻辑和状态转换编写 Vitest；对客户端交互至少完成构建、类型检查和浏览器烟测。需要验证：

- 顶栏刷新保留 URL。
- 筛选和选中任务可通过 URL 恢复。
- 操作面板展示目标、影响和原因要求。
- 校验失败保留输入。
- 操作成功后当前视图刷新且筛选不丢失。
- 键盘可打开、提交和关闭操作面板，焦点能够合理返回触发按钮。

### 11.3 页面验收

桌面和移动端分别验证：

1. 从 `/admin` 一步进入失租任务详情。
2. 从任务详情一步进入关联模型调用和审计记录。
3. 完成“重新执行”后仍停留在原任务上下文。
4. 查询失败与无数据有不同文案和视觉状态。
5. 普通用户仍无法发现或访问管理页面。
6. 页面和 API 不包含用户正文、模型 Prompt、Response、密钥或未脱敏错误。

完成实现后运行目标测试、完整 `npm test`、`npm run lint`、TypeScript 检查和 `npm run build`；任何无法运行的验证必须在交付说明中明确记录。

## 12. 实施边界

本次改造优先复用现有：

- `AdminShell`、`AdminNav`、`AdminSection`、`EmptyState`
- `AdminFilter`、`PageNav`
- `/api/admin/actions`
- `requireAdmin()`、`withAdmin()`
- 现有任务 mutation、审计和错误脱敏工具

允许针对当前目标进行小范围拆分：

- `AdminRefreshButton`
- `AdminActionPanel`
- `AdminAttentionQueue`
- `AdminTaskDetail`

不得顺带重写无关的用户、世界或模型业务逻辑，不新增第三方依赖。
