# 04 · AI 系统设计

> 更新日期：2026-07-27

## 1. 核心原则

1. **每轮只有一次 Narrator 调用。** 正文、时间变化、安全即时变化、对象轻行动、普通动态、重要事件变化、查探自报与神谕结果申报都来自同一个流式响应的 META；禁止为“世界自己发展”再调用第二个模型。
2. **输入统一由 LLM 理解。** Pantheon 与 Creator 共享正文入口；Creator 不区分“观测/改写”通道。只有推翻既成历史时返回 `retroactive_rewrite`，其余意图都按连续世界推进。
3. **Chapter 只作内部检查点。** Prompt 使用 `checkpoint window` / `world settlement`，不生成玩家可见章题，不要求玩家“结束本章”。
4. **时之仪决定默认跨度。** 玩家本轮明确写出的时间覆盖默认跨度但不改表盘；页面标题始终显示“世界名 + 纪元 + 时间”。
5. **关注不是立即行动。** 一次只能关注一个未解决事件；关注只提高后续 Context Builder 权重，不立刻生成正文或切场。

## 2. 单轮 Narrator 契约

流式响应由中文正文和一个严格 META 组成（正文之后另起一行 `<<<META`、一个 JSON、`META>>>`）：

```ts
type ContinuousNarratorMeta = {
  suggestions: string[];                     // 最多 4 条
  operation: "continue" | "retroactive_rewrite";
  temporalState?: { era?: string; time?: string };
  immediateChanges: ImmediateChange[];       // 最多 12 条
  worldActions: WorldAction[];               // 最多 3 条
  activityEntries: ActivityEntry[];          // 最多 3 条
  importantEventMutation?: ImportantEventMutation;
  significantEvent: boolean;
  settlementReasons: SettlementReason[];     // 最多 9 项枚举
  probeAttempted?: boolean;                  // 查探自报（仅诸神模式）
  revealedEventIds?: string[];               // 查探裁决揭示的隐藏编年史 id
  abilityReveals?: AbilityReveal[];          // 最多 12 条 hidden→rumored|known
  outcome?: {                                // 神谕结果申报
    result: "fulfilled" | "partial" | "thwarted" | "backfired";
    note: string;                            // 一句中文因由，最多 200 字符
  };
};
```

META 缺失或损坏一律容忍：`splitMetaBlock` 回退空 meta（`suggestions: []`），永不因此丢弃正文。

### 2.1 轻行动

`WorldAction` 指明 `actorType / actorId / action / targetIds / visibility / consequence`。actor 与 target 必须属于活动现实，actor 类型必须匹配 ID。`consequence` 只是后续叙事依据，不能绕过 `immediateChanges` 修改任意数据库字段。

### 2.2 一次性动态

`ActivityEntry` 只记录由本轮正文、轻行动或既有事件支持的 movement、rumor、omen、meeting、relation、conflict、discovery。不得为填满动态页制造无关新闻。

### 2.3 重要事件

`ImportantEventMutation` 每轮至多一项：

- `create`：建立 war、conspiracy、disaster、religious_conflict、faction_shift 或 world_crisis；
- `advance`：只可推进 Context Builder 明确提供的活动事件 ID；
- 事件阶段为 `emerging → developing → escalating → resolved`，允许按实际发展跳过中间阶段；
- 事件变化整项原子，非法时不得留下半个事件或孤立进展。

### 2.4 查探自报（probe_attempted）

仅诸神模式使用：当前玩家输入是世界内揭示隐藏真相的尝试（占卜、审问、查验记忆或痕迹、追查暗中行事者）时标 `true`——即使本轮没有收到查探裁决块也要标记，用于武装下一轮裁决。Creator 全知叙事无需查探裁决，恒为 `false` 或省略；正文中永不提及该标志。

服务端为“查探双门”：Context Builder 在玩家输入命中查探语义正则、**或**上一条 narrator 消息的 META 自报 `probeAttempted: true` 时附入隐藏裁决上下文。carry 只看最后一条 narrator 消息，下一条叙事落库后自然熄灭。

### 2.5 神谕结果申报（outcome）

仅当本轮正文对玩家神的神权行使或定向神谕做出裁定时申报：`fulfilled`（如愿）、`partial`（付出代价或不完全达成）、`thwarted`（被世界阻断）、`backfired`（尝试本身损害玩家神利益），`note` 为一句中文因由。裁定依据正文实际呈现的代价、限制、对手干预与凡人抗命；观察、对话或无定向漂移必须省略——不得为填字段编造结果。

## 3. Context Builder

动态上下文按以下优先级进入同一次 Narrator：

1. 当前关注事件及其最近进展；
2. 当前场景相关事件与行动；
3. 最近更新的重要事件；
4. 近期相关普通动态；
5. 既有世界卡、能力、世界书、编年史和正文滑动窗口。

上限为 3 个重要事件和 8 条动态。关注事件是“提高权重”，不是强制抢占场景。模型只能更新上下文中出现的 event ID，不能按标题猜测。

可见性在服务端组装上下文时就执行：

- Pantheon：只注入 `public`、`player_known`；
- Creator limited：复用 Pantheon 安全投影；
- Creator omniscient：可注入 hidden，但以“世界内尚未知晓”标注，NPC 仍不得因此获得知识。

## 4. 服务端应用与幂等

普通完成顺序：

```text
保存玩家消息
→ 保存 Narrator 正文
→ 应用时间与安全即时变化
→ 写入合法轻行动
→ 写入合法普通动态
→ 新建或推进重要事件及进展
→ 计算是否需要世界整理
→ 保存 durable completion
```

- 正文、时间、状态、动态和事件在同一应用事务中提交。
- 行动和普通动态逐项校验，坏项被过滤，不丢整轮正文。
- 重要事件变化整项校验。
- 数据库错误回滚整笔事务。
- generationId 派生消息、动态和事件稳定 ID；同一输出重放不会重复写入或重复推进。
- 追溯改写不向源现实写入正文或动态；Phase 4 在新现实完成克隆和校正后继续推进。

## 5. Durable 生成状态

普通正文生成状态机：

```text
reserved → context_ready → generating → output_stored → applying → completed
```

完整模型输出先以服务端私有快照保存：

```ts
{
  prose,
  parsedMeta,
  generatedAt,
  contractVersion
}
```

`output_stored` 表示 LLM 已完成、世界尚未应用。此阶段或 `applying` 失败时，“从此处重试”直接应用快照，不再次调用 Narrator。刷新页面从数据库恢复 `stage / retryable / safeError / updatedAt`；浏览器 SSE 断开只取消订阅，后台 owner 继续。

## 6. 世界整理与 Phase 4

世界整理仍是独立的后台深度任务，不是第二次 Narrator。Phase 4 按既定设计扩展整理结果：

- 合并语义重复的动态；
- 把达到阈值的普通冲突升级为重要事件；
- 推进、解决或派生持续事件；
- 事件 resolved 后清空 `focusedEventId`；
- 现实分叉后校正新现实事件图，源现实保持不变。

整理输出中还包含两类新增裁决：

- **将临之事状态裁决**（`canonEventUpdates`，最多 5 项）：对上下文列出的 `IMPENDING CANON EVENTS` 逐项裁定。状态机只允许 `pending → eligible|altered|cancelled|occurred` 与 `eligible → occurred|altered|cancelled`——枚举刻意不含 `pending`，事件不可回退为未裁决。`note` 为一句作者侧判定因由；`rumor` 仅 `status=eligible` 时给一句凡人视角传闻，绝不点破条件、机制或必然性。宽跨度检查点（数年及以上）须重审全部条目，场景级检查点极少改动超过一项。schema 上 `.default([])` 保证该字段引入前持久化的 `pendingSettlement` 断点续跑零影响。
- **纪元收束摘要**（`chronicle.eraDigest`）：仅当上下文提供 `== ERA TO CLOSE ==` 块时输出，`closedEra` 为被收束的纪元，`text` 为 150–400 字的史官纪元总评（该纪元的决定性冲突、变革与遗产）；否则省略。

整理任务使用同一真实进度协议和 durable 检查点；失败停在具体步骤，可继续而不重复已完成阶段。

## 7. 可见性矩阵

| 记录可见性 | Pantheon | Creator limited | Creator omniscient |
|---|---|---|---|
| `public` | 显示 | 显示 | 显示，标“世人皆知” |
| `player_known` | 显示 | 显示 | 显示，标“局部知晓” |
| `hidden` | 服务端过滤 | 服务端过滤 | 显示，标“天外批注 · 世界内尚未知晓” |

未读、关注和打开动态页都不改变知识状态。hidden 不能依赖 CSS 隐藏，也不能因 Creator 看见而泄露给世界内角色。

## 8. LLM 网关韧性（`src/lib/llm/gateway.ts`）

### 8.1 截断续写接力

- `CompletionRequest` 携带 `failOnTruncation` 标志：创世流式生成与所有 `completeStructured` 结构化任务开启；未开启的请求（普通正文流）保持单流行为。
- 三家适配器统一从结束原因映射 `truncated` 标志：OpenAI 兼容 `finish_reason=length`、Anthropic `stop_reason=max_tokens`、Gemini `finishReason=MAX_TOKENS`。
- 判定截断后发起续写请求：把已产出文本回填为 assistant 消息，再附一条固定 user 指令（从被截断的确切位置继续、不重复已输出字符、不加解释/前言/省略号/围栏）。
- 接缝去重：续写开头若与已产出结尾重叠，最多回看 400 字符裁掉重叠段；流式续写轮先攒足 400 字符的接缝缓冲再吐出去重后的文本。
- 单次请求最多接力 `MAX_CONTINUATION_ROUNDS = 12` 轮（12 × ~4k ≈ 48k，覆盖含将临之事的完整创世卡组并留余量）；超限抛中文错误，提示在香炉更换支持更长输出的模型或端点。

### 8.2 谎报截断启发式

部分中转通道截断输出却谎报正常结束（`finish_reason=stop`）。对“必须完整”的 JSON 输出做启发式判定：剥掉 ```` ```json ```` 围栏后以 `{` 或 `[` 开头、`JSON.parse` 失败、且字符串外花括号/方括号计数失衡（未闭合）即视为实际截断——与显式标志二者其一即触发续写（`needsContinuation`）。

### 8.3 流式断点续传

接力途中的瞬时网络错误（连接被掐断、上游过载）不废弃整条流：只要 `failOnTruncation` 开启、已累积文本非空、且未被玩家中止（AbortSignal），按指数退避（1s·2ⁿ + ≤500ms 抖动）以已累积文本为基础改走续写请求。预算 `STREAM_NETWORK_RETRIES = 4` 次，独立于接力轮数预算。

### 8.4 重试与非流式回退

非流式业务完成 `complete()` 先走流式传输（兼容中转站）：最多 3 次尝试，可重试错误为 HTTP 429/500/502/503/504/529、带上游语义的 404、以及网络断流类错误（`fetch failed` / `ECONNRESET` / `ETIMEDOUT` 等）；全部失败后允许一次非流式回退请求（`allowFallback`，默认开）。每次尝试与每轮续写均落 `LlmCall` 日志；网络类错误统一改写为面向玩家的中文提示。

### 8.5 创世任务瞬断自愈（`src/lib/genesis/task-runner.ts`）

- `isTransientLlmError` 复用网关的可重试判定。创世任务失败时若属瞬时故障且 `attempt < 3`（`MAX_TRANSIENT_ATTEMPTS`），回写 `queued`、清空错误、保留 `rawOutput` 断点，5 秒后自动重新认领执行；`attempt` 在租约原子认领时自增。
- 非瞬时错误终局 `failed`，错误信息脱敏（API 密钥掩码）并截断至 1000 字符。
- 手动重试接口（`POST /api/genesis/tasks/[id]/retry`）把 `attempt` 归零——给全新的瞬断自愈配额——并清空 `rawOutput` 重新排队。

### 8.6 创世定向修复两轮（`src/lib/genesis/generate.ts`）

流式创世产物校验失败（schema、模式匹配、引用校验、素材约束任一环节）进入定向修复，至多 `MAX_REPAIR_ROUNDS = 2` 轮：第一轮针对流式原文，第二轮针对第一轮修复稿的残余语义错误。每轮修复走 `completeStructured`（自身校验失败携错误重问 ×2，且同样开启截断续写接力），修复稿再次执行全部本地验证；两轮仍失败以最后错误终局。

### 8.7 创世语义质量门的多轮局部纠偏（`src/lib/genesis/semantic-gate.ts`）

完整卡组通过本地结构校验后进入语义审计。若初审含阻断项，质量门最多执行两轮“局部补丁 → 完整本地校验 → 复审”，因此一项任务最多产生三次语义审计。修复模型只返回 `{ path, action, valueJson }` 操作；服务端仅应用当轮审计明确列出的精确路径，未列出路径、数组重排和完整卡组重写一律不采纳。首轮复审发现关联残留时，第二轮以新的报告和上一轮已验证卡组为输入继续纠偏；第三次审计仍有 error 才终局失败，并持久化阻断详情供进度页展示。
